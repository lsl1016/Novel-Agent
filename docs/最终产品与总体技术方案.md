# 长篇小说 AI 创作平台：最终产品定义与总体技术方案

> **项目定位：长篇叙事运行时（Long-form Narrative Runtime）/ Novel Agent**

> 当前实现基线：Novel Agent V0.7（实体图 + 叙事图 + 检索与上下文编译器）

> 最终目标：让大模型能够在百万字级长篇创作中长期保持世界一致性、人物一致性、认知一致性和叙事结构一致性，并且整个创作过程可规划、可检索、可审查、可回退、可解释、可人工接管。

## 1. 最终要做的产品是什么

最终要做的不是一个“帮用户续写几段文字”的 AI 写作工具，也不是一个单纯的 RAG、知识库或知识图谱产品，而是一套面向长篇小说创作的 **Narrative Runtime（叙事运行时）+ 创作工作台**。

它的核心职责是：把长篇小说创作从“每次让模型凭上下文临时发挥”，升级成“模型在一个持续演化、可查询、可审计的故事世界中工作”。

产品的一句话定义：

> **通过世界模型（World Model）+ 叙事模型（Narrative Model）两类知识图谱、分层规划、上下文编译、版本化写作、自动审稿与有界自治，让大模型可以持续创作几十万到上百万字的长篇小说，同时保证世界事实、人物关系、能力体系、信息揭露和长期伏笔不失控。**

最终产品应同时提供两种形态：

1. **面向作者的创作工作台**：管理世界观、人物、剧情线程、章节计划、正文、审稿、时间线和知识图谱。
2. **面向 Agent/开发者的叙事运行时**：通过 MCP / HTTP / API 暴露所有创作能力，可被 Claude、Codex、ChatGPT、自研 Go Agent、IDE 或其他智能体系统调用。

因此，本项目的终局不是“AI Writer”，而是：

> **Long-form Narrative Operating System / 长篇叙事操作系统。**

## 2. 为什么需要这样一个系统

### 2.1 普通大模型在长篇创作中的根本问题

模型直接续写长篇小说，随着篇幅增长会持续出现：

- 人物年龄、身份、境界、位置和关系前后矛盾；
- 法宝、技能、血脉、势力等设定发生漂移；
- 已经死亡、损坏、离开的对象重新出现；
- 主角或视角（POV）角色知道了本不该知道的信息；
- 作者设定的世界真相提前泄漏到正文；
- 长期谜团、伏笔、情感债被遗忘；
- 每一卷都重新发明冲突，旧剧情无法“升值”；
- 上下文越来越长，但真正重要的信息反而被淹没；
- 计划、草稿和已提交正文互相污染；
- 自动写作一旦出错，没有清晰的人工接管和恢复点。

这些问题不是简单扩大上下文窗口（Context Window）就能解决的。真正缺少的是一个“外部故事状态系统”。

### 2.2 本项目的核心判断

长篇小说至少同时存在三类状态：

- **世界真实状态**：这个世界客观上发生了什么；
- **角色认知状态**：每个角色当前知道或相信什么；
- **读者认知状态**：读者到这一章被允许知道什么。

而长篇叙事的价值，往往来自三者之间的错位：

```text
世界真相（World Truth）
    ≠
人物认知 / 信念（Character Knowledge / Belief）
    ≠
读者认知 / 信念（Reader Knowledge / Belief）
```

因此系统不能只保存“事实”，还必须保存“事实如何被讲述”。

## 3. 从《逆天邪神》得到的产品方法论

参考《逆天邪神》的目的不是复制角色、文风或剧情，而是抽取可迁移的长篇叙事机制。

本项目已经确认最值得学习的是：

- 长线谜团不一次给完答案，而是分阶段推进；
- 线索、局部答案、错误认知、再解释和最终揭露形成阶梯；
- 旧剧情在后期被重新解释，从而“升值”；
- 世界观设定与人物关系、情感债和重大选择绑定；
- 跨卷叙事线长期存在，而不是每卷重新开始；
- 真相揭露不仅回答问题，还改变人物关系和世界认知；
- 一条线索只有在后续呼应（Callback）/ 揭示（Reveal）/ 兑现（Payoff）中被证明有功能，才升级为真正的伏笔。

因此参考图（Reference Graph）只保存：

- 叙事结构；
- 模式跨度；
- 线程生命周期；
- 信息释放节奏；
- 揭示 / 兑现结构；
- 信念反转 / 重新诠释（Belief Reversal / Reinterpretation）等模式。

它不应该自动把参考作品的角色、地名、法宝和正文注入新小说。

## 4. 最终产品的五条核心原则

### 4.1 参考图与故事图（Story Graph）永远分离

```text
参考图
= 用于学习“怎么写”
故事图
= 记录“自己的小说已经写了什么”
```

参考图数据只读，不能自动成为新小说正典（Canon）。

### 4.2 世界真相、角色认知和读者认知严格隔离

规划者（Planner）可以看到作者层真相；写作者（Writer）默认不能看到；审校者（Reviewer）可以在内部查看真相用于检测泄密，但反馈给写作者时必须脱敏。

### 4.3 规划、草稿、正典严格分离

```text
未来计划 ≠ 已发生事实
草稿内容 ≠ 已发生事实
通过提交闸门（Commit Gate）的版本 = 正典（Canon）
```

系统不能因为模型“打算这样写”就提前修改世界状态。

### 4.4 自动化必须有界

运行控制器（Run Controller）可以连续推进，但不能无限循环。所有自动推进都受：

- 最大章节数（max chapters）；
- 最大修订轮数（max revision rounds）；
- 压力阈值（pressure threshold）；
- 工具/模型超时（tool/model timeout）；
- 人工决策边界（human decision boundary）；
- 提交闸门；

约束。

### 4.5 所有关键检索和状态变化都应该可解释

系统必须能回答：

- 为什么这一章给写作者加载了这个人物？
- 为什么没有加载另一条叙事线？
- 这条人物关系来自哪个事件？
- 这条事实来自哪一章原文？
- 第 328 章写作者当时究竟知道什么？

## 5. 最终产品架构

![总体架构：六层结构](images/architecture-overview.png)

总体上分为六层。

### 5.1 产品与接入层

目标产品提供：

- Web / Desktop 创作工作台；
- 外部 IDE / Agent 接入；
- MCP 客户端；
- HTTP / Open API。

### 5.2 Skill 与 MCP 控制层

long-novel-writer Skill 负责：

- 创作流程纪律；
- 工具选择规则；
- 世界真相 / 写作者上下文边界；
- 章节提交规则；
- 人在回路（HITL）行为；
- 参考图谱的使用边界。

lsl1016/mcp-server 作为可选动态 MCP 网关，负责：

- 任意 HTTP JSON 接口动态注册成 MCP Tool；
- tools/list / tools/call；
- App 级授权；
- 只读 / destructive 标记；
- 审计；
- 限流；
- 多客户端统一接入。

当前 V0.7 Novel Agent 通过 MCP / HTTP Facade 暴露 77 个工具。

### 5.3 Novel Agent 运行时

核心运行模块包括：

- 故事架构师（Story Architect）/ 初始化；
- 规划运行时（Planning Runtime）；
- 检索与上下文编译器（Retrieval & Context Compiler）；
- 写作运行时（Writing Runtime）；
- 审校运行时（Review Runtime）；
- 小说运行控制器（Novel Run Controller）；
- 提交闸门；
- 人工决策 / 人在回路。

### 5.4 故事知识层（Story Knowledge Layer）

由两类互联知识模型组成：

- **世界模型（World Model）/ 实体图（Entity Graph）**：世界是什么；
- **叙事模型（Narrative Model）/ 叙事图（Narrative Graph）**：故事如何被讲述。

### 5.5 参考知识层（Reference Knowledge Layer）

参考图独立保存参考小说的结构化模式，不写入故事正典。

### 5.6 持久化 / 审计（Persistence / Audit）

当前运行时主要使用 SQLite 故事存储（Story Store）。最终产品应通过 Repository / Adapter 抽象持久化，使故事存储可根据规模迁移到 PostgreSQL、图数据库或组合存储，而不改变上层工具契约（Tool Contract）。

## 6. 两类知识图谱是整个产品的核心

![故事知识双模型：实体图与叙事图](images/story-knowledge-dual-model.png)

### 6.1 世界模型 / 实体图

实体图不是人物百科，而是整个故事世界的动态状态机。

当前已经包含的方向：

- 人物（Character）；
- 势力（Faction）；
- 地点（Location）；
- 物品 / 法宝（Item / Artifact）；
- 技能 / 境界（Skill / Realm）；
- 事件（Event）；
- 实体关系（Entity Relation）；
- 时间属性 / 时间关系（temporal attribute / relation）；
- narrative_entity_link。

最终需要升级成实体图 V2。

#### 6.1.1 身份（Identity）与角色（Role）

不能把所有“名字”都当成 alias。

需要区分：

```text
名字（Name）
别名（Alias）
身份档案（IdentityProfile）
角色 / 头衔 / 职位（Role / Title / Position）
转世 / 身体 / 性命（Incarnation / Body / Life）
```

这样才能正确表示：

- 本名；
- 假名；
- 伪装身份；
- 官职；
- 神位；
- 称号；
- 转世 / 身体 / 灵魂连续性。

#### 6.1.2 事件（Event）成为一等对象

最终的世界模型应该是事件中心（Event-Centric）的：

```text
Event
├─ participants
├─ participant_role
├─ location
├─ cause
├─ action
├─ outcome
├─ consequence
├─ state_change
└─ long-term impact
```

人物境界、关系、势力归属、法宝持有权等状态变化应尽量能追溯到事件。

#### 6.1.3 断言（Assertion）与证据（Evidence）

原文中的一句话并不一定是真相，因此需要：

```text
提及（Mention）
  ↓
断言（Assertion）
  ↓
已确认 / 已证伪 / 已被取代（confirmed / disproved / superseded）
  ↓
权威事实（Canonical Fact）
```

每条重要事实应该保存：

- chapter；
- source span；
- extractor；
- confidence；
- evidence；
- truth status；
- superseded_by。

#### 6.1.4 双时间模型

最终图谱不只保存章节有效区间，还要区分：

```text
valid_time
= 这个事实在故事世界里何时成立
knowledge_time
= 读者 / 角色从哪一章开始知道
```

这是长篇悬念和历史真相类作品的基础能力。

#### 6.1.5 力量 / 法宝 / 地理子图（Power / Artifact / Geography）

玄幻小说还需要专业子图：

- 力量图（Power Graph）：境界、血脉、传承、技能、体质、元素与使用条件；
- 法宝图（Artifact Graph）：持有、绑定、寄宿、器灵、封印、融合、觉醒；
- 地理图（Geography Graph）：世界、神域、大陆、区域、城市、宗门领地、秘境的空间层级。

### 6.2 叙事模型 / 叙事图

叙事图记录：

- 叙事线（NarrativeThread）；
- 谜团（Mystery）；
- 线索（Clue）；
- 伏笔（Foreshadowing）；
- 揭示（Reveal）；
- 兑现（Payoff）；
- 情感债（EmotionDebt）；
- 信念状态（BeliefState）；
- 叙事线阶段（Thread Stage）；
- 读者认知（Reader Knowledge）；
- 人物认知（Character Knowledge）。

它负责回答：

> 这个事实什么时候让谁知道？以什么形式知道？是否只是局部答案？是否存在错误认知？什么时候形成回收？

### 6.3 两类图必须交叉连接

典型关系：

```text
Mystery ── ABOUT ──> Character
NarrativeThread ── INVOLVES ──> Faction
Clue ── INVOLVES ──> Artifact
Reveal ── REINTERPRETS ──> Event
EmotionDebt ── BETWEEN ──> Character A / Character B
```

最终效果是：

> **实体图保存答案；叙事图保存答案如何被讲出来。**

## 7. 上下文编译器：连接知识与模型的核心层

V0.7 已经实现检索与上下文编译器。这是从“模型可以查知识图谱”升级到“系统主动给模型准备正确记忆”的关键一步。

### 7.1 为什么不能让模型自己不断查工具

如果写作者每章自行决定：

- 查谁；
- 查几跳；
- 查几条历史关系；
- 查哪个谜团；
- 查多少旧正文；

随着规模增长，检索行为会越来越随机。

因此系统统一执行：

```text
章节计划（ChapterPlan）
    ↓
锚点发现（Anchor Discovery）
    ↓
实体检索（Entity Retrieval）
    ↓
叙事检索（Narrative Retrieval）
    ↓
可见性过滤（Visibility Filter）
    ↓
章节快照过滤（Chapter Snapshot Filter）
    ↓
相关性排序（Relevance Ranking）
    ↓
令牌预算打包（Token Budget Packing）
    ↓
角色专属上下文（Role-specific Context）
```

### 7.2 规划者 / 写作者 / 审校者三套上下文

规划者上下文（Planner Context）：作者视角，允许看到世界真相、隐藏关系、长期计划和参考模式。

写作者上下文（Writer Context）：只包含读者 + 视角角色当前可知内容，并附带 forbidden_fact_keys，不提供隐藏真相值。

审校者上下文（Reviewer Context）：允许看到作者层真相，用于知识泄露、连续性、OOC（人物性格失真）、揭示强度和叙事职责检查。

### 7.3 时间切片

写第 N 章时，默认使用：

```text
权威故事快照（Canonical Story Snapshot）= 第 N - 1 章
```

未来状态不能提前进入当前上下文。

### 7.4 可解释检索

上下文快照（Context Snapshot）应保存：

- snapshot_id；
- chapter；
- snapshot_chapter；
- role；
- holder；
- token budget；
- compiled payload；
- retrieval trace。

通过 context_explain 能解释某条信息为什么进入上下文。

## 8. 规划系统：从百万字目标落到当前一章

最终规划体系采用多层规划，而不是一次规划几百章全文。

```text
小说蓝图（Novel Blueprint）
    ↓
故事架构师（Story Architect）
    ↓
篇章规划器（Arc Planner）
    ↓
滚动规划器（Rolling Planner）
    ↓
章节规划器（Chapter Planner）
    ↓
校验器（Validator）
```

### 8.1 蓝图（Blueprint）

保存相对稳定的高层意图：

- 核心主题；
- 世界基调；
- 主角核心矛盾；
- 终局真相；
- 长篇体验目标；
- 禁止改变的硬约束。

### 8.2 故事架构师（Story Architect）

最终目标是让用户输入一句或一段需求，例如：

> “写一部百万字东方玄幻，核心是身份谜题 + 世界真相反转。”

系统自动生成：

- 蓝图；
- 世界真相；
- 核心人物；
- 初始实体图；
- 5-10 条叙事线；
- 谜团；
- 情感债；
- 篇章 / 卷结构；
- 里程碑；
- 叙事线排期（Thread Schedule）；
- 第一阶段滚动计划。

### 8.3 滚动计划（Rolling Plan）

不冻结过远未来，采用：

- 硬视野（Hard Horizon）：约 5 章；
- 中视野（Medium Horizon）：约 20 章；
- 软视野（Soft Horizon）：约 50 章。

越靠近当前章节越具体，越远越抽象。

## 9. 写作运行时：正文不是直接从全局设定生成

写作者的输入必须来自安全写作者上下文（Safe Writer Context），而不是规划者上下文或数据库全量状态。

写作流程：

```text
章节计划
    ↓
writer_context_get / 上下文编译器
    ↓
安全写作者上下文
    ↓
写作者 LLM
    ↓
草稿 v1
```

每次修改都生成新的草稿版本（Draft Version）。

重要约束：

> **草稿 ≠ 正典。**

任何新版本都必须重新审校，不能因为旧版本通过审稿，就直接提交新版本。

## 10. 审校运行时：让系统自己发现长期写作错误

审稿分两层。

### 10.1 确定性审校（Deterministic Review）

适合结构化、可规则化的问题：

- 知识泄漏；
- 连续性；
- 叙事义务；
- 人物状态；
- 实体一致性；
- 境界 / 物品 / 关系 / 地点一致性。

### 10.2 语义审校（Semantic Review）

由模型处理语义问题：

- 语义知识泄漏；
- 语义人物一致性；
- 语义叙事质量；
- 节奏。

语义审校器可以内部读取世界真相，但返回给写作者的审校发现必须脱敏。

### 10.3 有界自动修订（Bounded Auto Revision）

系统允许自动修订，但必须：

- 创建新草稿；
- 全新审校；
- 有最大修订轮数；
- 不能自动覆盖 BLOCK；
- 遇到无法确定的问题转人工决策。

## 11. 运行控制器：把单章能力变成长期运行能力

运行控制器的职责不是替模型写文，而是持续组织：

```text
检查状态
→ 检查压力
→ 确保计划
→ 编译上下文
→ 写作
→ 审稿
→ 有界修订
→ 定稿
→ 提交
→ 推进游标
→ 报告
```

![单章创作闭环：计划 → 上下文 → 写作 → 审校 → 正典](images/chapter-creation-loop.png)

### 11.1 运行状态

- running（运行中）；
- paused（已暂停）；
- needs_author_decision（待作者决策）；
- completed（已完成）；
- cancelled（已取消）。

### 11.2 人在回路（HITL）

典型人工决策点：

- 故事压力超阈值；
- 规划者需要作者补世界设定；
- 章节计划被阻断；
- 写作者失败；
- 审校 / 修订无法通过；
- 定稿失败；
- 世界事实存在冲突；
- 实体断言无法确认。

needs_author_decision 是硬停止，不允许静默跳过。

## 12. MCP 与工具系统

工具系统是本项目对外的标准能力面。

当前 V0.7 已提供 77 个工具，主要分为：

| **工具域** | **作用** |
| --- | --- |
| 故事图 | 世界状态、剧情状态、章节提交 |

### 12.1 统一 HTTP Facade

所有工具可以统一暴露为：

```text
POST /api/agent/tools/call/{tool_name}
```

再由 lsl1016/mcp-server 动态注册成 MCP 工具。

### 12.2 权限分层

最终不要把所有工具授权给同一个 Agent。

建议至少拆成：

- 写作者 App：只拥有正文安全（prose-safe）查询 + 草稿写入能力；
- 规划者 / 作者 App：拥有作者视角、世界真相和计划修改能力；
- 审校者 App：拥有作者视角检查能力，但不直接修改正典；
- 控制器 App：拥有运行 / 提交 / 人在回路控制能力；
- 管理员 / 调试 App：拥有快照、证据、导入、修复工具。

readOnlyHint 只能表示工具是否产生副作用，不能替代业务权限。

## 16. 产品真正的护城河

这个产品真正的价值不在于“有一个更会写小说的 Prompt”，而在于以下几层同时存在：

### 16.1 持久故事状态

故事事实不依赖模型上下文临时记忆。

### 16.2 事实与叙事分离

知道“真相是什么”和知道“什么时候告诉读者”是两套不同模型。

### 16.3 外部上下文编译

不让模型每章自己决定该记住什么。

### 16.4 草稿 / 正典状态机

模型写出来的东西不会立即污染长期世界状态。

### 16.5 可持续长跑

运行控制器 + 审校 + 人在回路让系统可以连续推进，而不是一次一问一答。

### 16.6 可解释性

任何重要事实、关系、上下文、揭示都可以追溯原因和来源。

### 16.7 参考作品结构学习

参考图提供叙事模式参考，但不把参考作品的具体内容复制进新作品。

## 17. 最终产品成功标准

这个项目是否成功，不应该只看单章文笔，而应该看它能否完成：

> **在几十万到上百万字的创作跨度里，仍然能记住早期事实、合理演化世界状态、维持人物一致性、控制信息释放、持续推进长线叙事线，并让旧剧情在后期获得新的意义。**

因此最终 KPI 更接近：

- 低连续性错误率；
- 低知识泄漏率；
- 低实体冲突率；
- 高长期叙事线召回率；
- 高谜团 / 情感债闭环率；
- 上下文 token 不随章节线性失控；
- 人工介入次数可控；
- 自动修订收敛；
- 故事图可重放；
- 任意章节可解释“模型当时知道什么”；
- 参考模式迁移不产生内容复制。

## 18. 最终结论

本项目最终要做的是一个面向长篇小说的 **AI 叙事运行时 + 创作者工作台**。

它的核心不是单个大模型，而是一套持续运行的故事状态系统。完整闭环由 **参考知识 → 故事架构师 / 规划 → 世界模型 + 叙事模型 → 上下文编译器 → 计划 / 写作 / 审校 / 修订 → 提交闸门 → 权威故事状态** 串联，并在每章完成后继续推进下一章。

最终，AI 不再是“每章重新读提示词后猜接下来怎么写”，而是在一个持续演化、具有世界状态、认知状态、叙事义务、审稿规则和工具能力的运行时中创作。

这也是整个项目最重要的产品定位：

> **让大模型拥有可以长期维护的“世界记忆”和“叙事记忆”，从而具备真正的长篇小说持续创作能力。**
