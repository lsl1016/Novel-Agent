# Phase C 产品方案与形态：一句话开书

> 状态：产品方案（2026-10-02），与技术设计稿 `docs/phase-c-design.md` 配套阅读。
> 本文回答"用户拿到什么、怎么用"；技术稿回答"系统怎么造"。

## 1. 产品定位（一句话）

**把"开一本新书"从"会写 JSON 的工程师活"变成"说一句话、看一页纸、点头开跑"的分钟级体验。**

Phase C 是整个平台的**冷启动入口**。Runtime 的全部能力（双图、规划、编译、审校、长跑）都已存在，但今天启动一本新书必须手写 ~90 个对象的 `architecture.json`——这是产品最大的单点门槛。Phase C 之后的用户漏斗变成：

```text
一句创意 → 5 分钟出「开书档案」→ 作者点头/改几处 → 第 1 章自动开写
```

## 2. 解决的痛点（现状对照）

| 现状 | Phase C 之后 |
|---|---|
| 开书需手写 architecture.json（15 个分组、6 类跨引用） | 一句话 + 可选参数 |
| 写错引用只能靠 dry-run 报错逐条排 | 生成器保证引用自洽 + 校验器兜底 + 自动修复 |
| "百万字"与骨架规模脱节（弧排 60 章就没了） | 规模公式 + 覆盖率硬校验 |
| 想改一个人物要重写整份 JSON | 分段产物可局部重生（改 S2 只重跑 S3-S5） |
| 新用户无法评估"这本书值不值得跑" | 一页纸开书档案：真相/线程/弧线/假设全透明 |

## 3. 目标用户与典型场景

| 用户 | 场景 | 用哪条路径 |
|---|---|---|
| **网文作者**（有点子，没大纲） | "写一部百万字东方玄幻，身份谜题+世界反转"——要快速看到这本书的骨架长什么样，不满意就调 | 共创模式（Agent 对话） |
| **尝鲜/评估用户** | 第一次接触平台，想 30 分钟内看到"AI 能不能写出像样的第一章" | 闪电模式（一条命令） |
| **严谨作者**（已有部分设定） | 手里有世界观笔记/人物卡，要合成进骨架再开跑 | 工匠模式（改 stages/架构 JSON） |
| **外部 Agent / 开发者** | 程序化创建书籍、批量试验不同开局 | API / MCP 工具 |

## 4. 产品形态

Phase C 在 **Phase D 工作台之前**落地，因此产品形态是三入口 + 一份核心读件，全部为 Phase D 的"开书向导"预留 UI 化路径：

| 形态 | 载体 | 面向 | 说明 |
|---|---|---|---|
| **Agent 对话**（主打） | Claude/ZCode + narrative-kg MCP + long-novel-writer Skill | 作者/尝鲜用户 | 用户自然语言说创意、提修改，Agent 调 `novel_architecture_generate`、呈现开书档案、代改代跑。零 UI 时代的"产品本体" |
| **CLI** | `novel-story create-from-idea` | 高级用户/脚本/演示 | 一条命令完成 生成→校验→落盘（→可选 apply→可选 --run N） |
| **API / MCP 工具** | `novel_architecture_generate`（第 92 个工具，planner/admin 白名单） | Agent/开发者 | 返回 architecture + 校验报告，与 `story_architect_apply` 两步走 |

**核心读件：开书档案（Story Bible Draft）**。新增的人可读 Markdown 产物（`bible.md`），这是作者审阅的界面——不看 JSON。结构：

```markdown
# 《书名》开书档案
## 一句话核心承诺（core_promise）
## 本次生成采用的假设        ← auto 模式的推断全透明，逐条可否决
## 主角与核心人物            ← 表格：身份/初始状态/与主角关系
## 世界真相与揭示计划（作者可见，读者不可见）
                            ← 表格：真相摘要 / 保密级 / 第 N 章后才向读者揭示
## 叙事线一览                ← 表格：线程 / 类型 / 引入章 / 兑付窗口
## 篇章结构                  ← 表格：弧 / 章节范围 / 主要目标 / 出口条件
## 首弧里程碑与排期
## 校验结论                  ← 0 error；warnings 逐条列出
```

## 5. 三档使用模式

| 模式 | 交互 | 流程 | 耗时 |
|---|---|---|---|
| **闪电**（默认） | 一条命令，零交互 | idea → S1-S4 → 校验 → 落盘；`--apply --run 3` 一路到第 3 章正文 | 生成 ~2 分钟；+3 章 ~30 分钟 |
| **共创** | 对话式，两处暂停 | idea → **S1 后暂停**：呈现一页纸蓝图（书名/题材/核心承诺/主角/结局倾向）→ 用户点头或重定向 → S2-S4 → 呈现完整开书档案 → 确认 → apply | 10-20 分钟（含对话） |
| **工匠** | 手改文件，局部重生 | 生成后手改 `stages/s2.json` → 只重跑 S3-S5 → 重校验；或直接改 `architecture.json` 过 dry-run | 自定 |

**为什么共创模式只在 S1 后暂停一次**：蓝图阶段重定向成本是 1 次模型调用，结构阶段重定向是整套重生。产品把最贵的认知决策（"这是不是我想写的书"）前置到最便宜的确认点；之后的细节修正全部走"局部重生"，不再整锅重造。

## 6. 核心用户旅程

**旅程 A：闪电开书（尝鲜）**

```text
$ novel-story create-from-idea --db my.db \
    --idea '写一部百万字东方玄幻，身份谜题+世界真相反转' \
    --apply --run 3
→ 生成中: 蓝图✓ 实体✓ 叙事✓ 结构✓  校验: 0 error, 2 warnings
→ 已应用 (蓝图1/真相3/实体11/线程8/弧7/里程碑21)
→ 开跑: 第1章 计划✓ 草稿✓ 审校✓ 提交✓ ... 第3章✓
→ 正文见 story-data/my-novel/novel.md; 档案见 bible.md
```

**旅程 B：共创访谈（作者）**

```text
作者: 写一部都市悬疑，法医主角，单元案串主线
Agent: (interview, ≤4 问, 每问给选项)
       1. 单元案密度? [每3-5章一案|每8-12章一案]
       2. 主角性别年龄倾向? 3. 禁忌内容? 4. 结局倾向?[真相大白|留白]
作者: 每5章一案 / 女,35岁 / 不要血腥细节 / 真相大白
Agent: (S1) 一页纸蓝图 → 作者: "书名换掉, 主角改成前法医"
Agent: (S2-S4) 完整开书档案 → 作者: "把'哥哥失踪'线兑付提前到第二卷"
Agent: 局部重生 S4 → 复核 → apply → "要现在开跑第 1 章吗?"
```

**旅程 C：已有设定合成（严谨作者）**

```text
作者提供: 世界观笔记.md + 人物卡.md（自由文本）
Agent: 结构化抽取 → 作为 S1/S2 的强约束输入（生成不得违背已给设定）
     → 未覆盖处照常生成并标注"推断"
```

**旅程 D：外部 Agent（开发者）**

```text
tools/call novel_architecture_generate {idea, options}
→ {architecture, validation, assumptions}
→ 程序审阅/用户审阅 → tools/call story_architect_apply
→ tools/call novel_run_start(1)
```

## 7. 关键交互设计

1. **假设透明**：auto 模式下所有推断（题材细分、主角设定、结局倾向、章长）写入 `bible.md` 的"假设"节**并逐条编号**；对话中说"假设 2 改成 X"即可定向重生。作者永远知道哪些是自己的意志、哪些是机器的猜测。
2. **分层确认**（共创模式）：S1 蓝图一页纸 → 确认；S4 后完整档案 → 确认。中间不问（细节问题属于章节计划的 author_questions，已有机制，不提前打扰）。
3. **伏笔即承诺**：开书档案的"叙事线/真相揭示"表格让作者在开跑前就看见全部长期承诺及其兑付窗口——这是平台的差异化：别家给你一段爽文，我们给你一张**可核销的承诺清单**，长跑中的审校器逐章盯着它。
4. **真相隔离在产品层延续**：开书档案含世界真相（作者视角读件），但通过 Agent 分享给"读者视角"的场合由权限层拦（writer 角色调不到生成工具与 apply）；`bible.md` 属作者私有目录。
5. **改稿即重生局部**：所有修改落到 stages 分段文件上，最小范围重跑；每次重生后的 diff（新增/移除/变更的键）在对话中呈现，避免"改一处、全文面目全非"。
6. **永不静默 apply**：默认停在 dry-run 报告；`--apply` 与 Agent 的 apply 动作都必须是显式指令。

## 8. 用户产物清单

```text
story-data/<slug>/
  bible.md               ← 开书档案（人读，审阅界面）
  architecture.json      ← 机器可应用版本（可直接 apply-architecture）
  idea.json              ← 原始创意 + 参数 + 假设
  validation.json        ← 校验报告 + 修复轮次
  stages/s1…s4.json      ← 分段产物（局部重生的改稿面）
  novel.md               ← (--run 后) 正文导出,持续追加
```

## 9. 产品原则与边界

1. **生成的是骨架，不是书**：Phase C 承诺到"可开跑的正典起点 + 首章启动"，不承诺正文质量——那是写作运行时 + 审校 + 校准的职责。营销与文档措辞遵守此边界。
2. **架构是种子不是锁**：apply 后一切仍可用既有工具逐项修改；开书档案标"v1"，后续演进由工作台（Phase D）承接。
3. **同一道闸门**：生成物、外部手写架构、未来 UI 表单，全部过同一个确定性校验器。产品永远不因"是 AI 生成的"而绕过校验。
4. **失败要好看**：校验不过时呈现的是"哪三条假设冲突、建议改哪"的人话，不是 JSON 错误栈。
5. **不做**：不生成正文、不替作者做终局性创作决策（结局倾向等只采纳用户输入或标注为假设）、不做 UI（Phase D）、不接入付费/账号体系。

## 10. 成功指标

| 指标 | 目标 | 度量点 |
|---|---|---|
| 冷启动时长（创意→第 1 章提交） | < 30 分钟（闪电模式） | C3 演示实测 |
| 一次通过率（真创意首过 dry-run 0 error） | ≥ 80% | 生成日志统计 |
| 假设否决率 | 每次生成被改假设 ≤ 1/3（否则说明推断太冒进） | idea.json vs 最终版 diff |
| 开书→追跑转化 | 创建的书 ≥ 60% 跑到 10 章以上 | runs 表 |
| 题材泛化 | ≥ 3 个题材（玄幻外至少 2 个）一次通过 | C3 双题材 + 后续抽样 |
| 生成成本 | ≤ 7 次模型调用 / ~60k token | stages 耗时/token 记录 |

## 11. 里程碑（与设计稿 C1/C2/C3 对齐）

| 子阶段 | 产品验收 |
|---|---|
| C1 核心闭环 | CLI + service 生成→校验→落盘；真创意一次过 dry-run；`bible.md` 初版（表格齐全，无 diff 视图） |
| C2 共创打磨 | interview 模式、分层确认、局部重生 + diff 呈现、`story_architect_apply` 校验升级合入（外部作者同闸门）；旅程 C 设定合成 |
| C3 全链路演示 | `--apply --run 3` 一条命令到第 3 章；双题材验证；README 快速开始改写为"一句话开书"；对外演示脚本（闪电模式 5 分钟演示流） |

## 12. 与 Phase D 的衔接

Phase C 的三入口即 Phase D 工作台"开书向导（New Novel Wizard）"的三块拼图：对话访谈 → 向导聊天面板；开书档案 → World Bible 工作区的种子文档；stages 局部重生 → 向导的"重生成此节"按钮。Phase C 落地时即冻结这三者的数据契约（bible.md 结构、stages 文件格式、假设编号规范），Phase D 只做 UI 化不改语义。

## 13. 产品风险与对策

| 风险 | 对策 |
|---|---|
| 生成骨架"千书一面"（套路化） | counter_expectation 输入位 + prompt 反俗约束 + 题材泛化指标盯防 |
| 作者被 90 项细节吓退 | 分层确认：作者只看一页纸蓝图和开书档案两张表，细节默认托管给假设机制 |
| 一次通过率不达标 | 有界修复回路（技术稿 §3 S5）+ 阶段内即时校验；仍不够则加"校验错误→人话建议"映射表 |
| 生成质量好但前 3 章留不住人 | 不是 Phase C 的锅但影响漏斗：C3 演示流固定配"开书档案+第 1 章"组合呈现，并回收跑批数据给写作校准 |
| 用户把开书档案分享导致剧透 | 档案头部署名"含世界真相·作者私有"；Agent 侧靠权限白名单拦截 |
