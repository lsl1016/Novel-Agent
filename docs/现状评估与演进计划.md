# Novel Agent 现状评估与演进计划

> 本文是《最终产品与总体技术方案》的配套执行文档，基于 2026-10 对 V0.7 代码库的全量评审（源码约 4400 行逐行阅读、测试实跑、关键行为实测）与后续架构讨论的结论。上位文档回答"最终做什么"，本文回答"现在到哪了、先做什么、不做什么"。

## 1. 现状结论

### 1.1 V0.7 声明与实际相符

- 77 个工具三方一致（`tooldefs.py` / `server.py` / `registration/mcp-server-batch-create.json` 逐一核对无多无少）。
- 测试套件实跑 **46/46 passed**（约 2.7s）。
- skill 与工具一一对应：`skills/long-novel-writer` 的 12 个 references 覆盖全部工具域；`dist/` 为字节级一致的打包副本。
- Reference Graph 只读边界真实存在：`reference.py` 仅返回结构元数据，不返回原文。

### 1.2 核心机制是真实落地，不是纸面架构

- **认知隔离三重裁剪**：secret 别名/属性/关系在 `entity_graph.py` 过滤；隐藏 World Truth 对 Writer 只给 `forbidden_fact_keys` 不给值（`context_compiler.py` `_forbidden_facts`）；`private_author` 阶段对 Writer 不可见；语义审稿返回前经 `redact_hidden_values` 脱敏。
- **Context Compiler（736 行）**：确定性评分（ChapterPlan 直引 0.30 / POV 0.20 / 跨层链接 0.15 / recency 梯度 / 2-hop 弱扩展 0.025）、三角色预算（writer 12k / planner 24k / reviewer 20k + 分区软上限）、超预算尾部裁剪、digest 命名不可变快照 + `context_explain` 可解释检索；时间切片严格用 N-1。
- **Commit Gate 有牙**：`chapter_finalize` 强制计划重验、要求精确 draft version 的完整 reviewer 集合、BLOCK 不可静默覆盖（override 必须给理由）、planned reveal 未声明直接 BLOCK（`service.py:648`）。
- **Run Controller** 是持久化状态机（runs / events / decisions / reports 四表），`needs_author_decision` 硬停止，决策未解决禁止 resume。
- **零依赖设计**：LLM 调用 urllib 直连 OpenAI 兼容 API，planner/writer/reviewer/revision 四角色独立环境变量带 fallback 链；stdio / HTTP / facade 鉴权 / 网关批量注册（注册脚本按网关 120s 超时收紧 `novel_run_continue.max_steps≤3`、`chapter_auto_revision_loop.max_rounds≤3`）。

### 1.3 完成度判断

| 维度 | 完成度 | 说明 |
|---|---|---|
| 运行时基座（V0.7 范围） | ~70-80% | 双图谱 V1、隔离、编译器、门禁、HITL 均已实现 |
| 知识层深度（Phase A） | 未开始 | Identity/Event 一等化/Assertion/双时序/专业子图全部缺失 |
| 长跑验证（Phase B） | 约为零 | 无任何真实生成章节，阈值与 token 预算均未校准 |

| 产品工作台（Phase D） | 约为零 | 9 个工作区无代码；权限分层停留在文档建议 |

对照最终产品整体完成度约 **30-40%**。剩余部分不是均匀缺口——最难的部分（百万字一致性是否成立）尚未被验证。

## 3. 总体路线

在原方案 Phase A→D 之前插入 **Phase A0（可靠性与闭环地基）**。理由：Phase A 要改 schema，没有迁移框架和事务边界会把 P1 问题放大；候选晋升闭环又是 Assertion/Evidence 的最小落地路径。

```text
A0 地基（1-2 周量级）
  ├── schema 迁移框架 + 连接/事务语义集中
  ├── chapter_commit 单事务化
  ├── extraction_candidates 晋升闭环（= Assertion/Evidence 地基）
  ├── 仓储层重构（SQL 收敛，手写 SQL 保留，不引 ORM）
  └── 堵 chapter_commit 旁路
        ↓
Phase A：Entity Graph V2（先设计文档后代码）
        ↓
Phase B：真实 Narrative Stress Test（尽早，优先级高于加功能）
        ↓ （权限分层与 B 并行）
Phase C：Story Architect 收尾（一句话建小说）
        ↓
Phase D：产品化工作台
```

## 4. Phase A0：可靠性与闭环地基

### 4.1 schema 迁移框架（不引第三方）

- DDL 收敛到单一 `schema.py`，改为有序迁移列表 `MIGRATIONS = [(1, "v0.7 基线"), (2, "V2 identity/event 表"), ...]`。
- 版本号用 SQLite 内建 `PRAGMA user_version`（零额外表）：启动时读版本 → 事务内依序应用未执行迁移 → 写回。新库走全量，老库原地升级。
- 每个迁移幂等可重入。

### 4.2 连接与事务语义集中

- `connect()` 统一设置 `PRAGMA foreign_keys=ON`（修 #5）、`journal_mode=WAL`、`busy_timeout`。
- 新增 `store.transaction()` 上下文管理器；`chapter_commit`（提交正文 + declared updates + 抽取）包进单事务，失败整体回滚（修 #4、#9）。

### 4.3 候选晋升闭环（最优先单项）

给 `extraction_candidates` 补三个工具：

- `candidate_list`：按章节/类型/状态列出；
- `candidate_promote`：晋升为正典实体/事实，必须写入证据链（chapter、source span、extractor、confidence）；
- `candidate_reject`：标记拒绝，留审计。

此闭环即方案 6.1.3 `Mention → Assertion → confirmed → Canonical Fact` 的最小实现，Phase A 的 Assertion/Evidence 表直接在其上演进。

### 4.4 仓储层重构

- 原则：**保留手写 SQL**（时序图查询是领域逻辑本身，ORM 反而埋掉 N-1 快照等关键语义），**只搬家**。
- 按聚合补齐：`WorldRepository`（world_facts+beliefs：belief_snapshot / forbidden / truth ledger）、`CanonRepository`（chapters+events+character_states），与既有 `EntityGraph` / `WritingStore` / `PlanningStore` 并列。
- 立规矩：service / context_compiler / run_controller 禁止直接 `connect()`，只调仓储方法。
- 收益：Phase A 改表时受影响查询收敛在 2-3 个文件；将来迁 PostgreSQL 时仓储层即多方言落点。

### 4.5 门禁旁路修复

- `chapter_commit` 从公开工具面撤下（降为 finalize 内部调用），或要求 controller 显式 `override_reason`。

### A0 验收标准

> **状态:已于 V0.8 完成,证据见 `docs/a0-implementation-report.md`,测试 52/52。**

- [x] 旧库打开自动迁移，`user_version` 正确递增；中途断电重开可续跑
- [x] `chapter_commit` 中途 kill -9 后库内无半提交状态（单事务回滚 + 回归测试）
- [x] 幽灵外键插入被拒绝（回归用例固化 #5 的实测）
- [x] 候选从抽取 → 晋升 → 出现在 `entity_author_get` 全链路可演示
- [x] 工具 schema 不变（对外兼容），service 层无内联 SQL（工具面变更：chapter_commit 移除 + candidate 三工具，77→79）

## 5. Phase A：Entity Graph V2（先设计文档，后动代码）

落地顺序（每步带 V0.7→V2 数据迁移）：

> **进展（2026-10，V0.9）**：1-3 项与因果追溯已实现（86 工具、58/58 测试），证据见 `docs/phase-a-v2-report.md`；双时序 per-holder 落账与专业子图为下一批。

1. **Identity / Role** ✅：`identity_profiles` + life 连续性（本名/假名/伪装/官职/神位/转世），别名不再与身份混用；
2. **Event 一等化** ✅：participants / participant_role / cause / outcome / state_change；人物境界、关系、归属、持有权变化挂 `event_id` 可追溯；
3. **Assertion / Evidence** ✅（接 A0 候选闭环）：接 A0 候选闭环，命题状态机 confirmed / disproved / superseded + superseded_by；
4. **双时序** ✅（per-holder 披露表 fact_disclosures，reveal_after 语义兼容并自动同步）：`knowledge_time` 落到 per-holder 信念表 `(fact_key, holder, valid_from, known_from)`，替代全局 `reveal_after` 闸门——这是关系表最擅长、图库反而不擅长的建模；
5. **专业子图** ✅（power_context_get / artifact_history_get / geography_tree_get 聚合视图，基于既有原语不新增表）：Power / Artifact / Geography（含持有史、境界进程、空间层级）。

配套：从 `stages` / `mysteries` / `debts` 反推初始 Event 的迁移脚本；Extraction Pipeline V2 设计（对应"当前最大缺口"末项）。

## 6. Phase B：真实 Narrative Stress Test（优先级高于加功能）

**动机**：reviewer 阈值、pressure 参数、token 预算（12k/24k/20k、各分区百分比）目前全是未校准值；系统从未跑过连续长篇。方案的核心赌注——百万字一致性——处于未验证状态。

> **进展(2026-10,V0.10 后)**:长跑基建已就绪——双协议 LLM 客户端(OpenAI + Anthropic Message)、`env/llm.env` 端点配置、`scripts/stress/`(种子架构/smoke/drive/metrics,见其 README)。发起:`python3 scripts/stress/drive.py --db story-data/stress.db --seed --target-chapter 40`。

**做法**：配置 planner/writer/reviewer/revision 四个模型角色，用 CLI（或 8.2 的无人值守脚本）连续生成 **30-50 章、10-15 万字**玄幻测试小说。

**量化 KPI**（对照方案第 17 章）：

- Continuity Error Rate / Entity contradiction / Knowledge leak（含语义改写式）/ OOC count
- Open Mystery accumulation / Overdue Foreshadowing / Overdue EmotionDebt / Thread dormancy
- Context token growth 曲线（是否随章节线性失控）/ Auto revision rounds / Human intervention count

**产出**：用实测数据回头校准 Context Compiler 权重与预算、reviewer 判定阈值、pressure 参数；顺带验证网关 120s 超时下 `max_steps≤3` 的碎片化影响。

## 9. 明确不做的事（决策记录）

| 决策 | 理由 |
|---|---|
| **不自研通用 Agent Runtime** | 方案 7.1（检索权收归确定性 Compiler）与 4.4（有界自治）已明确否定自由 agent loop；服务端已内嵌受控模型调用环（plan_generate / draft_generate / auto_revision_loop / run_step），转移条件由代码而非模型现场决定。引入自主漫游 77 工具的 agent 等于把已解决的问题请回来 |
| **不装图数据库** | 知识图谱由 SQLite 关系表编码（node/edge 模式是图库内核结构）；单本小说规模（几千实体、查询 ≤4 跳）SQLite 绰绰有余。当前建模缺口（Event/Assertion/Identity/双时序）全是 schema 深度问题，与引擎无关。换引擎信号：① Assertion 行数十万级 + 并发写 → PostgreSQL（方案 5.6 本就如此规划）；② 语义检索 → sqlite-vec/pgvector |
| **不引 ORM** | 零依赖是明确设计目标；核心查询（时间切片、belief 快照、可见性过滤）手写 SQL 比 ORM 更清晰。缺的是仓储分层，不是抽象框架 |
| **不为写作流程引入工作流引擎** | 门禁已在服务端代码（finalize 前置条件、BLOCK 不可覆盖、HITL 硬停）；缺的只是权限分层堵旁路与工具面收敛 |

**运行环境结论**：无需安装任何知识图谱软件。运行仅需 Python ≥3.10 + `pip install -e mcp-server`（零强制依赖）+ 一个 OpenAI 兼容 LLM API（环境变量配置）。不配 API 时确定性部分（规划/编译/确定性审稿/图谱/Run 手工流程）全部可用，AI 环节返回 `*_NOT_CONFIGURED`。
