# Novel Agent V0.5 — 小说运行控制器

## 目的

V0.5 把章节事务变成一个持久化、有界的运行控制器。它将重复性的编排自动化,但不会把模型当作不受约束的自主作者。

## 运行状态机

```text
running
  ├─> paused
  ├─> needs_author_decision
  ├─> completed
  └─> cancelled
```

一次运行会在同一个故事数据库(Story DB)中存储 `run_id`、起始/当前/最后已提交章节、章节数、停止配置、停止原因、事件、决策与周期性报告。

## 单章节事务

1. 检查目标/停止条件。
2. 检查叙事/结构压力。
3. 确保滚动规划窗口存在。
4. 复用有效的章节计划(ChapterPlan),或调用作者规划器(Author Planner)。
5. 生成/复用带版本的草稿。
6. 运行确定性审校 + 可选的语义审校。
7. 执行有界的自动修订。
8. 对精确获批的草稿版本执行定稿。
9. 推进运行游标并持久化事件/报告。
10. 停止或继续。

任何控制器路径都不会绕过正常审校闸门;自 v0.8 起 `chapter_commit` 已从公开工具面移除,正典提交唯一入口是 `chapter_finalize`。

## 作者规划器边界

`planner_context_get` 有意包含世界真相(作者独有)。它只用于作者规划,绝不能传给负责正文的写作者。

`chapter_plan_generate` 返回结构化计划,然后运行与手动规划相同的章节计划校验器。如果规划器发出 `author_questions`,自动推进即告停止,而不是凭空编造持久的世界真相。

## 停止条件

一次运行可能因以下原因完成/停止:

- 达到 `target_chapter`;
- 达到 `max_chapters`;
- 到达目标篇章的目标结尾;
- 超过压力阈值;
- 章节计划缺失/被阻塞;
- 规划器/写作者/审校者模型故障;
- 审校/修订循环耗尽或停滞;
- 定稿闸门失败;
- 显式的人工暂停/取消。

`novel_run_continue` 每次调用最多以 50 个章节步为上限;正常交互操作中请使用小得多的数值。

## 人工决策

需要作者裁决的控制器故障会存储在 `novel_run_decisions` 中,并把运行状态改为 `needs_author_decision`。

典型恢复流程:

1. `novel_run_decision_list`。
2. 检查证据。
3. 修复章节计划、草稿、故事状态或外部模型配置。
4. 可选地在裁决中修补安全的运行配置。
5. 以 `action=resume` 调用 `novel_run_decision_submit`。
6. 继续同一次运行。

控制器绝不会凭空捏造缺失的作者选择,也绝不会自动使用 BLOCK 覆盖。

## 压力策略

运行控制器不会仅仅因为未来的硬窗口(Hard-window)计划尚未填满就停止;它可以自行创建这些计划。压力停止关注的是叙事积压与结构性逾期事项,例如叙事线排期/里程碑,或一个已被阻塞的计划。

## 报告

`novel_run_report` 记录已提交章节摘要、事件阶段计数、当前规划/故事压力、未决决策与停止原因。`report_every` 会在每 N 个成功章节之后自动持久化检查点。

## 崩溃/重启恢复

运行状态持久化在 SQLite 中。使用同一个故事数据库重新连接,并调用 `novel_run_status`。中断前已达成正典提交的章节不应通过新运行重新生成;而应恢复既有的运行游标。
